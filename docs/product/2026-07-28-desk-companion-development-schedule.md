## 1. 排期目标

本计划用于把 Desk Companion v1 PRD 转换成可以逐项执行、验收和调整的开发任务。

最终交付目标是：

> 一台未配置 WiFi 的全新设备，接通电源后 5 秒内进入固定黑色 Normal 眼睛并自然眨眼；用户可通过 Web 选择 8 种表情、按需开启 AUTO、设置昵称和开机短句，并在手机首屏完成常用操作。

计划不追求一次完成所有潜在功能。开发顺序固定为：

1. 先保证离线摆件成立。
2. 再建立统一表情系统。
3. 再加入可重复生产的个性化。
4. 最后整理 Web 体验和主题。
5. 通过实机和小批量使用决定下一版。

## 6. 阶段 1：离线摆件模式

**时间：2026-07-31 至 2026-08-05**
**目标：无论网络状态如何，设备都优先作为动态摆件运行。**

### 6.1 技术决策

本阶段采用最小状态机改动：

1. `PROVISIONING` 继续负责 LAN 相关服务的首次初始化。
2. 服务初始化完成后，不等待 WiFi 连接成功，直接进入 `LAN_IDLE`。
3. `LAN_IDLE` 不再因 `!wifi.isConnected()` 自动跳回 `PROVISIONING`。
4. `WifiConfigService` 在后台维持 AP、连接、重试和慢速重试。
5. 配网状态通过 Web 查看，不持续占用 TFT。
6. 暂不新增复杂的“屏幕配网入口”状态。

这样可以保留现有服务生命周期，同时减少对状态机结构的重写。

## 7. 阶段 2：统一表情与可选 AUTO

**时间：2026-08-06 至 2026-08-17**
**目标：完成 v1 最核心的“生命感”体验。**

### 7.1 技术拆分

本阶段不立即删除 `EyesView`。先在现有模块中建立稳定接口，再决定是否重命名为 `ExpressionView`。

建议数据模型：

```cpp
enum class ExpressionId : uint8_t {
    NORMAL,
    HAPPY,
    SLEEPY,
    SLEEPING,
    CURIOUS,
    SURPRISED,
    GRUMPY,
    LOVE
};

enum class ExpressionMode : uint8_t {
    AUTO,
    MANUAL
};
```

表情系统分为三层：

```text
Web / 状态事件
    ↓
DisplayService：决定 AUTO、MANUAL 或信息模式
    ↓
IdleBehaviorService：决定 AUTO 当前行为
    ↓
EyesView / ExpressionView：只负责绘制与逐帧更新
```

### 7.2 表情制作顺序

| 批次 | 表情 | 原因 |
|---|---|---|
| 第一批 | Normal、Happy、Sleeping、Curious | 可复用现有眼睛和 Squish 逻辑 |
| 第二批 | Sleepy、Surprised、Grumpy、Love | 需要增加新的几何绘制 |

所有表情先使用程序化图形，不加入全屏位图。

### 7.4 AUTO 调度规则

AUTO 调度必须满足：

- Normal 是开机默认基础状态，AUTO 仅由用户主动开启。
- 眨眼属于 Normal 内部微动画，不算一次完整表情切换。
- Normal 眼位固定，不进行左右移动；眼睛本体不受主题配色影响，始终为黑色。
- Curiosity、Happy、Surprised 是短暂事件，结束后回 Normal。
- Sleepy 可以持续更久，Sleeping 只在低频或夜间出现。
- 同一事件不能连续两次。
- 切换时间由区间随机生成，不能每隔固定秒数执行。
- Web 手动操作和开发者状态拥有更高优先级。

建议优先级：

```text
系统错误/配网明确提示
    >
用户 Web 手动表情
    >
开发者实时状态
    >
信息页
    >
AUTO 自主行为
```

如用户关闭开发者状态，则 Web 手动表情不应被 Hook 覆盖。

### 7.5 API 契约

#### 获取列表

```http
GET /expressions
```

```json
{
  "expressions": [
    {"id": "normal", "label": "Normal"},
    {"id": "happy", "label": "Happy"}
  ]
}
```

#### 获取当前状态

```http
GET /expression/current
```

```json
{
  "mode": "auto",
  "selected": "normal",
  "rendered": "curious"
}
```

`selected` 表示用户选择，`rendered` 表示 AUTO 当前实际显示。

#### 设置表情

```http
POST /expression
Content-Type: application/json

{"mode": "manual", "id": "happy"}
```

恢复 AUTO：

```json
{"mode": "auto"}
```

## 14. 风险与应对

| 风险 | 预警信号 | 应对 |
|---|---|---|
| 状态机改动影响现有功能 | 信息页无法恢复、服务未初始化 | 阶段 1 只做最小状态改动 |
| 表情代码重复膨胀 | 每个表情复制 update 逻辑 | 共用几何和动画状态 |
| AUTO 看起来随机但体验机械 | 事件按固定顺序、频率过高 | 权重、时间区间和不连续重复 |
| Boot 个性化增加启动时间 | 超过 5 秒才看到眼睛 | 限制动画时长和文本数量 |
| Web 改动导致 Flash 超限 | 应用程序分区继续超过 92% | 去除页面重复来源，资源放 LittleFS |
| 外部服务影响基础动画 | 断网时卡顿或页面停住 | 网络更新非阻塞，摆件优先 |
| 实机验证发现屏幕差异 | 不同批次颜色、偏移、闪烁不同 | 阶段 5 使用 3 台同配置样机 |
| 排期被新功能打断 | 开发中加入头像、声音或 App | 新需求统一进入 v1.1 backlog |

## 15. 变更控制

开发开始后，新需求必须回答三个问题：

1. 是否直接增强“生命感、互动或个性化”？
2. 是否会影响当前里程碑日期？
3. 是否可以放入 v1.1 而不损害 v1 核心体验？

满足以下任一条件，默认进入 backlog：

- 需要新增硬件。
- 需要云服务或账号。
- 需要大容量图片或中文字体。
- 需要改变现有主板或外壳。
- 预计超过 1 个工作日且不影响 P0 验收。

排期调整时优先级为：

```text
保住离线表情
    >
保住 8 种表情和 AUTO
    >
保住昵称定制
    >
保住 Web 易用性
    >
主题和导入导出
    >
附加信息功能优化
```
