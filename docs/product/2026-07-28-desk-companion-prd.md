# Clawd Mochi 桌面电子摆件产品需求文档

> 日期：2026-07-28
> 状态：规划完成，待确认后实施
> 产品阶段：DIY 小批量验证
> 目标版本：Desk Companion v1

## 1. 文档目的

本文档用于确定 Clawd Mochi 下一阶段的产品方向、功能边界和开发顺序。

本阶段不把产品建设成企业设备、效率工具或通用物联网平台，而是把它做成一个：

> 通电就会自己活动、可以简单控制、能够个性化的桌面电子摆件。

后续开发以“放在桌面上是否有趣、是否愿意经常看一眼”为主要判断标准，而不是继续堆叠信息页面。

---

## 2. 产品决策摘要

### 2.1 产品定位

Clawd Mochi 是一个 USB-C 供电的像素桌面伴侣。它通过 240×240 彩色屏幕表现眼睛、情绪和轻量信息，平时会自主眨眼、张望、发呆和休息，用户也可以通过手机网页切换表情和调整设置。

### 2.2 核心价值

1. **通电就有生命感**：不配网、不打开网页，也能作为完整摆件使用。
2. **简单可互动**：手机连接后可以立即切换表情、颜色和显示内容。
3. **每一台可以不同**：支持昵称、开机短句、主题和定制表情。
4. **功能是点缀**：时钟、天气、番茄钟和开发者状态是附加能力，不抢占摆件的主体验。

### 2.3 首发版本建议

| 版本 | 内容 | 建议价格 |
|---|---|---:|
| 标准版 | 固定外壳、默认主题、完整表情和网页控制 | 129–139 元 |
| 定制版 | 标准版 + 昵称 + 开机短句 + 配色 + 定制表情 | 169–189 元 |

首批建议采用 `129 元标准版 / 169 元定制版`，制作 10 台以内验证需求。

### 2.4 已确定的范围

- 保持 ESP32-C3、ST7789 1.54 英寸屏幕和 USB-C 供电。
- 保持本地 Web 控制，不开发手机 App。
- 默认体验为表情摆件，配网不是首次开机的强制步骤。
- 保留时钟、番茄钟、天气、行情和开发者状态，但不继续优先扩展信息页。
- v1 不增加账号、云服务、电池、语音和复杂传感器。

## 3. 目标用户与使用场景

### 3.1 目标用户

#### A. 桌面摆件用户

- 喜欢像素风、电子摆件或桌搭。
- 不关心开发工具集成。
- 希望通电后就能看到可爱的动态内容。

#### B. DIY 和极客用户

- 喜欢 ESP32、开源硬件和自己折腾。
- 会使用网页控制、天气、行情或开发者状态功能。
- 愿意尝试后续固件和主题更新。

#### C. 个性化礼物用户

- 希望显示名字、祝福、纪念日或宠物形象。
- 更看重“这是专门为我做的”，而不是功能数量。

### 3.2 核心场景

1. 用户把设备放在显示器旁，接通 USB-C，设备直接进入自主表情。
2. 用户工作时偶尔看到它眨眼、张望、打瞌睡或变换情绪。
3. 用户用手机网页选择喜欢的表情和背景颜色。
4. 用户切换到时钟、天气或番茄钟，短暂作为信息屏使用。
5. 定制版用户在开机时看到自己的昵称、祝福或专属表情。

### 3.3 用户不应该被迫完成的事情

- 首次开机必须先配置 WiFi。
- 安装 App 或注册账号。
- 理解局域网、UDP、Hook 或开发板术语。
- 为了看到基本表情而依赖互联网。
- 在复杂设置页中寻找常用表情。

## 4. 核心卖点

### 4.1 卖点一：它会自己活动

设备的核心不是“显示一双眼睛”，而是让用户感到它有自己的状态。

待机行为至少包括：

- 自然眨眼。
- 左右张望。
- 短暂停顿和发呆。
- 困倦、闭眼和恢复。
- 偶尔出现开心或惊讶等短表情。
- 避免固定周期和机械重复。

目标效果：用户不进行任何操作时，设备仍然值得摆在桌面上。

### 4.2 卖点二：表情可直接互动

Web 首页首先展示表情，而不是设置和信息面板。

用户应该能在两次点击内完成：

- 切换表情。
- 恢复自动待机。
- 更换背景色。
- 调节亮度。

表情选择后应立即显示，不要求保存按钮。

### 4.3 卖点三：低成本个性化

定制能力需要标准化，避免每个订单都修改源代码。

v1 支持：

- 设备昵称。
- 两行开机短句。
- 默认背景颜色。
- 默认表情。
- 标准版内置主题选择。

昵称和短句优先支持 ASCII 字母、数字和常用符号。中文需要单独解决字体空间问题，不作为首个开发阻塞项。

### 4.4 卖点四：轻量实用

以下功能作为“偶尔有用”的附加卖点保留：

- 时钟。
- 番茄钟。
- 天气。
- Crypto 和 Market。
- Claude Code / Codex 类开发者状态。
- 网页画板。

默认首页和开机流程不突出这些功能。用户主动选择后才进入信息模式。

## 6. v1 功能需求

### 6.1 P0：摆件核心体验

#### FR-01 离线优先启动

**需求**

- 无论是否保存过 WiFi，设备启动后都应先进入表情模式。
- 未配置 WiFi 时，设备继续提供 AP 和 Web 配置入口，但不持续占用屏幕显示配网说明。
- 配网入口可以通过 Web 设置页访问。
- 配网失败或断网时，表情动画不能中断。

**验收标准**

- 全新设备通电后 5 秒内显示动态眼睛。
- 不连接热点、不配置网络，设备可以持续运行表情至少 24 小时。
- 用户仍可连接设备热点并完成配网。
- 网络断开后，设备回到表情而不是停留在错误页。

#### FR-02 统一表情系统

**需求**

建立统一的 `ExpressionId`，将表情状态与具体绘制逻辑分开。v1 至少提供：

| 表情 | 行为 |
|---|---|
| Normal | 正常睁眼、自然眨眼 |
| Happy | 向内弯曲或 Squish 笑眼 |
| Sleepy | 半闭眼、缓慢眨眼 |
| Sleeping | 闭眼，可带简化 Z |
| Curious | 眼睛偏向一侧并停留 |
| Surprised | 眼睛变宽或变方 |
| Grumpy | 斜眼或压低上眼线 |
| Love | 爱心或爱心提示符 |

**验收标准**

- 8 种表情可在 Web 中直接选择。
- 每种表情在 240×240 屏幕上具有清晰差异。
- 表情切换不产生明显全屏闪烁。
- 表情名称、枚举、Web API 和 UI 使用同一份映射。

#### FR-03 自动待机行为

**需求**

- 增加 `AUTO` 模式，作为默认模式。
- AUTO 模式以 Normal 为主，随机插入眨眼、张望、困倦、开心和惊讶等短行为。
- 行为间隔使用范围随机值，不采用固定周期。
- 同一短行为不得连续出现两次。
- 用户手动选择表情后保持该表情，直到用户选择 AUTO 或设备按配置超时恢复。

**建议规则**

| 行为 | 建议间隔/权重 |
|---|---|
| 眨眼 | 3–10 秒 |
| 张望 | 10–30 秒 |
| 开心 | 30–90 秒，低权重 |
| 惊讶 | 45–120 秒，低权重 |
| 困倦 | 60–180 秒，夜间提高权重 |

**验收标准**

- 连续观察 10 分钟不会呈现明显固定循环。
- 动画过程中 Web 控制仍可立即抢占。
- 切换信息页再返回时，AUTO 状态可以正确恢复。

#### FR-04 设备昵称与开机短句

**需求**

- 设置页增加设备昵称和两行开机短句。
- 数据保存到 NVS，并在重启后保留。
- 开机动画使用保存后的内容。
- 提供恢复默认值入口。

**字段限制**

| 字段 | 限制 |
|---|---|
| 设备昵称 | 1–12 个 ASCII 字符 |
| 开机第一行 | 0–16 个 ASCII 字符 |
| 开机第二行 | 0–16 个 ASCII 字符 |

**验收标准**

- Web 修改后无需重新烧录。
- 输入过长时 Web 和固件都执行限制。
- 空值、异常字符或存储失败不会导致开机异常。
- 恢复默认后显示标准品牌开机画面。

#### FR-05 表情控制 API

**需求**

- 提供读取表情列表、当前表情和设置表情的稳定 API。
- 保持现有快捷命令兼容，Web 新页面改用语义化接口。

**建议接口**

```text
GET  /expressions
GET  /expression/current
POST /expression
```

设置请求示例：

```json
{
  "id": "happy",
  "mode": "manual"
}
```

**验收标准**

- 非法表情返回明确的 `400`。
- 设置成功后响应中包含实际生效的表情。
- AUTO 和手动模式均可读取。

### 6.2 P1：可售卖体验

#### FR-06 Web 首页重排

首页信息优先级调整为：

1. 当前表情预览和 AUTO 开关。
2. 表情选择网格。
3. 背景颜色和亮度。
4. 时钟、番茄钟、天气等功能入口。
5. 高级设置和网络设置。

验收标准：

- 手机首屏可以看到当前表情和至少 4 个表情入口。
- 常用表情切换不需要展开设置面板。
- 高级功能保留，但不干扰第一次使用。

#### FR-07 主题预设

v1.1 提供至少 4 组主题：

- Classic Orange。
- Dark Orange。
- Mint。
- Pink。

每个主题定义背景色、前景色、默认表情和夜间亮度建议值。

#### FR-08 自动昼夜性格

- 可选择跟随时间进入夜间行为。
- 夜间降低亮度并提高 Sleepy/Sleeping 的出现概率。
- 无网络时间时保持普通 AUTO，不阻塞使用。

#### FR-09 定制配置导入导出

- Web 可以导出设备个性化配置为 JSON。
- 可导入配置快速制作下一台定制设备。
- 配置只包含显示和偏好，不包含 WiFi 密码和日志。

该功能用于降低定制版的制作成本，也便于用户备份设置。

### 6.3 P2：后续增强

以下需求在 v1 小批量验证后决定是否实施：

- 低色深像素头像导入。
- 节日和季节表情包。
- 用户自定义表情序列。
- 蜂鸣器提示音。
- 触摸或实体按键切换表情。
- 光敏自动亮度。
- Home Assistant / MQTT。

头像导入不能直接保存全尺寸 RGB565 图片。应先评估 LittleFS 空间，并优先考虑 1-bit、4-bit 调色板或较小分辨率资源。

## 7. 关键体验流程

### 7.1 首次开机

```text
接通 USB-C
    ↓
短开机动画（可显示昵称）
    ↓
直接进入 AUTO 表情
    ↓
后台启动设备热点
    ↓
用户需要设置时才打开 Web
```

### 7.2 手动切换表情

```text
打开 Web 首页
    ↓
看到当前表情和表情网格
    ↓
点击 Happy
    ↓
屏幕立即显示 Happy
    ↓
点击 AUTO 后恢复自主行为
```

### 7.3 定制版制作

```text
卖家连接设备
    ↓
填写昵称和开机短句
    ↓
选择主题和默认表情
    ↓
导出订单配置留档
    ↓
重启检查并完成交付
```

## 8. 非功能要求

### 8.1 性能

- 通电后 5 秒内进入表情。
- Web 表情命令在局域网内 300 ms 内开始生效。
- 表情动画不出现持续可见的全屏闪烁。
- 网络请求不得阻塞表情动画。

### 8.2 稳定性

- 离线表情模式连续运行 24 小时无卡死。
- 连续切换表情 100 次无异常。
- 断网、重连和第三方接口失败不影响基础摆件功能。
- 配置写入中断不能使设备无法启动。

### 8.3 资源约束

- 实施 P1 前将应用程序分区使用率降低到 90% 以下，或明确调整分区方案。
- 新增表情优先使用程序化图形，不使用大量全屏位图。
- 避免为每种表情复制完整动画状态机。
- Web 资源继续关注内嵌字符串与 LittleFS 文件重复的问题。

### 8.4 易用性

- 普通用户无需阅读开发者文档即可使用表情。
- 所有设置有默认值，错误输入不会破坏显示。
- 恢复默认配置后仍能离线作为摆件使用。

## 9. 技术实施规划

### 9.1 建议模块

| 模块 | 职责 |
|---|---|
| `ExpressionView` | 根据 `ExpressionId` 绘制和更新表情 |
| `IdleBehaviorService` | 调度 AUTO 模式下的随机行为 |
| `PreferenceService` | 保存昵称、开机短句、默认表情和 AUTO 设置 |
| `DisplayService` | 管理表情视图与信息视图切换 |
| `BootAnimation` | 读取并显示个性化开机内容 |
| `WebService` | 提供表情和个性化配置 API |

现有 `EyesView` 可以逐步演进为 `ExpressionView`，不要求一次性重写所有显示逻辑。

### 9.2 对现有代码的预计改动

| 路径 | 预计改动 |
|---|---|
| `src/view/eyes_view.*` | 增加表情枚举、各表情绘制和动画状态 |
| `src/service/display_service.*` | 增加 AUTO/手动表情模式和切换逻辑 |
| `src/service/preference_service.*` | 增加昵称、短句、默认表情持久化 |
| `src/view/boot_animation.*` | 支持个性化文本 |
| `src/states/provisioning_state.*` | 取消未配网时强制占屏 |
| `src/states/lan_idle_state.*` | 将自主表情设为默认体验 |
| `src/service/web_service.*` | 增加语义化表情 API 和 UI |
| `scripts/test_web_ui.py` | 增加表情、AUTO 和个性化设置回归 |

### 9.3 实施原则

- 先改变启动和待机体验，再增加新表情。
- 先建立统一表情模型，再扩展表情数量。
- 个性化必须通过配置完成，不能依赖每单修改代码。
- 每个阶段保持现有时钟、天气、行情和开发者状态可用。
- 每完成一个阶段都执行干净固件构建和 Web 回归。

## 10. 开发路线

### 阶段 0：基线固定

**预计工作量：1–2 天**

- 记录当前固件大小和可用 LittleFS 空间。
- 补充当前启动流程、表情入口和设置持久化测试。
- 确认标准版默认颜色、昵称和开机内容。

**完成条件**

- 当前版本可重复构建。
- 回归测试结果有明确基线。
- 产品默认配置不再变化。

### 阶段 1：离线摆件模式

**预计工作量：2–4 天**

- 修改未配网启动流程。
- AP 和 Web 在后台运行。
- WiFi 状态不再长期占用屏幕。
- 验证断网不影响表情。

**完成条件**

- 全新设备无需配网即可作为摆件使用。
- 配网能力仍然可访问。

### 阶段 2：统一表情与 AUTO

**预计工作量：5–8 天**

- 建立统一表情枚举和绘制入口。
- 完成 8 种基础表情。
- 增加随机待机调度。
- 增加表情 API。

**完成条件**

- AUTO 模式连续运行 24 小时。
- 8 种表情均可从 Web 切换。
- 没有明显闪屏或模式切换回归。

### 阶段 3：个性化

**预计工作量：3–5 天**

- 增加昵称和两行开机短句。
- 增加默认表情配置。
- 改造开机动画。
- 增加配置校验和恢复默认。

**完成条件**

- 制作定制版不再需要修改和重新编译源代码。
- 所有定制项重启后保留。

### 阶段 4：Web 首页与主题

**预计工作量：3–5 天**

- 将表情和 AUTO 放到手机首屏。
- 增加主题预设。
- 整理高级功能入口。
- 增加配置导入导出。

**完成条件**

- 新用户在 30 秒内可以完成表情和颜色切换。
- 标准版和定制版均可通过同一套 Web 页面配置。

### 阶段 5：小批量验证

**预计工作量：至少 2 周自然使用时间**

- 制作 3 台内部样机。
- 完成 24 小时运行、断电、断网和手机端测试。
- 制作不超过 10 台的首批版本。
- 收集买家最常使用的表情和功能。

**完成条件**

- 首批设备没有集中出现同一故障。
- 配网和基本控制不需要卖家反复解释。
- 能确定用户愿意为哪些定制项付费。

- 24 小时联网运行。

## 12. 成功指标

DIY 小批量阶段不接入云端数据分析，使用人工记录。

| 指标 | 首批目标 |
|---|---:|
| 通电后无需说明即可看到表情 | 100% |
| 买家独立完成网页连接 | ≥80% |
| 设备基础功能故障率 | <5% |
| 因“不知道怎么玩”产生的咨询 | <20% 订单 |
| 定制版订单占比 | ≥30% |
| 用户主动展示或发送桌面照片 | ≥20% |

最重要的验证不是行情、天气调用次数，而是：

- 用户是否愿意长期把它放在桌面上。
- 用户是否愿意选择定制版。
- 哪些表情最常被选择和分享。

## 13. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 功能继续膨胀 | v1 只接受增强生命感、互动或定制的需求 |
| 表情增加导致代码重复 | 先建立统一表情模型和共享动画状态 |
| 动画与网络请求互相阻塞 | 所有行为使用非阻塞更新，不在绘制路径等待网络 |
| 字体和素材占用过大 | v1 个性化先限制 ASCII，图像使用低色深方案 |
| Web 页面越来越复杂 | 表情首屏，高级功能分区收纳 |
| 定制订单不可复制 | 所有定制项配置化，并支持导入导出 |
| 摆件必须配网才能使用 | 离线表情作为不可破坏的基础能力 |

## 14. 暂不实施

以下内容不进入 Desk Companion v1：

- 手机原生 App。
- 用户账号和云同步。
- 云端设备管理后台。
- 语音助手。
- 摄像头和麦克风。
- 电池和充电管理。
- 表情商店或会员体系。
- 自定义脚本运行环境。
- 大规模在线固件分发系统。
- 重新设计主板。

这些方向只有在首批用户明确提出、且能显著提高购买意愿时再评估。

## 15. 下一步决策

建议按以下顺序进入实施：

1. 确认本文档中的产品定位和 P0 范围。
2. 确认首发默认主题、8 种表情名称和定制字段限制。
3. 从 **阶段 1：离线摆件模式** 开始开发。
4. 阶段 1 验收通过后，再进入统一表情系统，避免同时改动启动状态机和全部绘制逻辑。

第一项实施任务建议定义为：

> 让一台从未配置过 WiFi 的设备通电后，5 秒内进入 AUTO 表情，同时保留后台热点和配网能力。

这是整个产品路线的基础。该任务完成后，Clawd Mochi 才真正从“需要配置的开发板项目”变成“通电就能使用的桌面电子摆件”。
